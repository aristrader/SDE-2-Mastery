# Builder — Lombok variant

The same Builder pattern as `simple_builder/`, but with the boilerplate generated by Lombok's `@Builder` annotation. This trades hand-written control for brevity &mdash; you get the shape for free, but lose required-field enforcement and validation.

## The code

```java
@Builder
@ToString
public final class JobOffer {
  private final int salary;
  private final String city;
  private final int joiningBonus;
  private final int relocationBonus;
  private final int performanceBonus;
}
```

That's it. `@Builder` generates everything else at compile time.

## What `@Builder` generates

When applied to a class, Lombok produces:

| Generated member | Detail |
| --- | --- |
| Package-private all-args constructor on `JobOffer` | Used by the generated `build()` method |
| Static nested class `JobOfferBuilder` | One private field per declared field, fluent setters returning the builder |
| `JobOfferBuilder.build()` | Just calls the all-args constructor &mdash; no validation |
| `public static JobOffer.builder()` | Static entry-point method on the product, returning a fresh `JobOfferBuilder` |

Call site:

```java
JobOffer offer = JobOffer.builder()
    .salary(150_000)
    .city("HYDERABAD")
    .joiningBonus(20_000)
    .build();
```

Note the entry point: `JobOffer.builder()` &mdash; a static method on the *product*, not `new JobOffer.JobOfferBuilder()`. This is idiomatic, hides the implementation-detail class name, and reads more naturally in a fluent chain.

## What you give up vs the hand-written variant

### No required-field enforcement

`JobOffer.builder().build()` compiles and returns an offer with `salary = 0` and `city = null`. Every field is optional from the compiler's perspective. The hand-written variant takes required fields in the Builder constructor, so the compiler refuses to start a chain without them.

### No validation

The generated `build()` just calls the constructor. There is no place for rules like "total bonuses must not exceed salary."

### Two recovery routes

If you need validation while keeping `@Builder`:

**Option A &mdash; manually declare the builder class.** Lombok merges its generated members into your declaration and skips generating a method you've already declared:

```java
@Builder
public class JobOffer {
  // ... fields ...

  public static class JobOfferBuilder {
    public JobOffer build() {
      validate();
      return new JobOffer(salary, city, joiningBonus, relocationBonus, performanceBonus);
    }
    private void validate() { /* ... */ }
  }
}
```

Awkward because you have to know the field order to call the all-args constructor.

**Option B (cleaner) &mdash; declare your own all-args constructor with validation.** Lombok uses any all-args constructor it finds rather than generating one:

```java
@Builder
public class JobOffer {
  // ... fields ...

  private JobOffer(int salary, String city, int joiningBonus,
                   int relocationBonus, int performanceBonus) {
    if (salary <= 0) throw new IllegalStateException(...);
    // ...
    this.salary = salary;
    // ...
  }
}
```

Validation runs in the constructor, which the generated `build()` always calls. This is the better trade-off for most codebases.

## Why `@Setter` is wrong on a `@Builder` class

`@Builder` and `@Setter` are opposing patterns:

| Annotation | Style | Mutability of product |
| --- | --- | --- |
| `@Builder` | EJ Builder | Immutable, fields stay `final` |
| `@Setter` | JavaBeans | Mutable, fields non-final |

Stacking `@Setter` on a `@Builder` class either does nothing (because all fields are `final`) or breaks the immutability guarantee. The whole reason to use Builder is to avoid setters.

## Why `JobOffer.builder()` has no `new` keyword

`builder()` is a static method on `JobOffer`, not a constructor:

```java
public static JobOfferBuilder builder() {
  return new JobOfferBuilder();   // 'new' lives in here, hidden from callers
}
```

Strictly per Effective Java Item 1, this is *not* a static factory method *for* `JobOffer` &mdash; it returns a `JobOfferBuilder`, not a `JobOffer`. It's a static entry-point method that returns a builder. The Item-1 benefits (named call site, hides concrete return type, no `new` exposure) still apply, just not as a factory for `JobOffer` itself.

## When to reach for this variant

- The product is simple, the contract is permissive, and Lombok is already on the classpath.
- You're prototyping or writing internal data classes where required-field enforcement is overkill.
- You'll add validation in a custom constructor (Option B) when needed.

## When to prefer the hand-written variant

- Required-field enforcement matters at compile time.
- Validation logic is non-trivial (especially cross-field).
- You want full control over the builder's class name, method names, and field order.
