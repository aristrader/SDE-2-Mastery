# Web Security: XSS, SOP, CORS, and Browser Isolation

## Attack Models & Threat Boundaries

A fundamental principle of web application security is that different defensive controls operate at distinct threat boundaries. Treating security as a single generic layer leads to incorrect architectural assumptions.

Security models are structured around the attacker's capabilities:

1. **Level 1 - Network Attacker (Public Wi-Fi, Compromised ISP, Packet Sniffer):**
   - **Capability:** Intercept, inspect, or tamper with packets in transit between the client and server.
   - **Defense:** **TLS/HTTPS** encrypts and authenticates transport traffic.
   - **Boundary Limitation:** TLS secures transport in transit, but does not validate the semantic safety of data generated by the server or executed by the browser.

2. **Level 2 - XSS Attacker (Injected Client-Side Script Execution):**
   - **Capability:** Execute arbitrary JavaScript within the origin of the victim's active browser session.
   - **Defense:** **Context-aware Output Encoding**, **HTML Sanitization** (for rich text), **Content Security Policy (CSP)**, and **HttpOnly cookie flags**.
   - **Boundary Limitation:** If malicious script executes in the browser origin, transport encryption (TLS) cannot prevent client-side execution.

3. **Level 3 - Browser Storage Theft (Local Credential Extraction):**
   - **Capability:** Access local device files or browser storage (`localStorage`, `sessionStorage`, IndexedDB) via local malware, malicious extensions, or physical device access.
   - **Defense:** Ephemeral session tokens, secure hardware enclaves, OS-level file encryption.
   - **Boundary Limitation:** Data stored in `localStorage` or `sessionStorage` is directly accessible to any script executing in that origin.

4. **Level 4 - Full Device Compromise (Host Takeover):**
   - **Capability:** Root/administrator control over the OS, kernel memory, processes, and browser runtime.
   - **Outcome:** **Full compromise.** Application-level browser security controls (such as CORS, SOP, or HttpOnly) cannot defend against a compromised operating system.

## Cross-Site Scripting (XSS)

In an XSS attack, an attacker tricks a web application into delivering malicious script to a victim's browser, where it executes with the full privileges of the vulnerable origin.

```
+-------------------------------------------------------------------------+
|                              XSS Flavors                                |
+-------------------------------------------------------------------------+
|  Stored XSS     | Injected payload persisted in server DB -> rendered   |
|                 | to all users viewing that stored record.              |
+-----------------+-------------------------------------------------------+
|  Reflected XSS  | Injected payload in request (URL/query/body) echoed   |
|                 | immediately in response page without persistence.     |
+-----------------+-------------------------------------------------------+
|  DOM-based XSS  | Malicious source read by client JS and passed to an   |
|                 | execution sink entirely within the browser DOM.       |
+-------------------------------------------------------------------------+
```

### Stored XSS Flow
1. Attacker submits a payload (e.g., `<script>stealToken()</script>`) via a comment or profile form.
2. The server stores this payload in the database without sanitization.
3. A victim navigates to the comments page.
4. The server queries the database and renders the HTML response, embedding the unescaped script.
5. The victim's browser executes the script in the context of the trusted origin.

### Reflected XSS Flow
1. Attacker crafts a malicious link: `https://example.com/search?q=<script>evil()</script>`.
2. Victim clicks the link.
3. The server takes the `q` parameter and echoes it directly into the HTML response: `<p>Results for <script>evil()</script></p>`.
4. The victim's browser executes the injected script upon parsing the server's response.

### DOM-based XSS Flow
1. Attacker crafts a link with a malicious payload in a client-readable fragment: `https://example.com/app#default=<img src=x onerror=evil()>`.
2. Victim visits the link. The request to the server may not even contain the fragment `#...`.
3. Client-side JavaScript reads from an untrusted **source** (e.g., `location.hash`, `location.search`, `document.referrer`).
4. Client-side JavaScript writes that data to an unsafe execution **sink** (e.g., `element.innerHTML = payload`, `document.write(payload)`, or `eval(payload)`).
5. The browser executes the script directly in the DOM without the payload ever needing server-side reflection.

### Primary Defenses & Engineering Rules

```
+-----------------------------------------------------------------------------+
|                          Primary Defense vs Defense-in-Depth               |
+-----------------------------------------------------------------------------+
| Context-Aware Output Encoding | Primary defense for rendering untrusted data|
| HTML Sanitization             | Used ONLY when deliberately allowing HTML   |
| Content Security Policy (CSP) | Defense-in-depth layer restricting resources|
+-----------------------------------------------------------------------------+
```

1. **Context-Aware Output Encoding (Primary Defense):**
   - Untrusted data must be encoded according to the exact context where it is inserted:
     - **HTML Body:** Convert `&` -> `&amp;`, `<` -> `&lt;`, `>` -> `&gt;`, `"` -> `&quot;`, `'` -> `&#x27;`.
     - **HTML Attributes:** Escape attribute boundaries so strings cannot break out of quotes (`<input value="{{input}}">`).
     - **JavaScript Context:** Use safe serialization (e.g., JSON encoding with HTML-entity escaping) rather than direct string concatenation into `<script>` blocks.
     - **URL Parameters:** Percent-encode query components; ensure URL schemes are allowlisted (e.g., blocking `javascript:...` pseudo-protocols in `href`).
2. **Sanitization vs Output Encoding:**
   - **Encoding** transforms executable control characters into benign display text. This is the required default for plain text data.
   - **Sanitization** (e.g., DOMPurify) parses HTML and strips disallowed tags/attributes while preserving safe formatting (e.g., `<b>`, `<i>`, `<p>`). Use sanitization **only** when the business requirement explicitly mandates accepting and rendering formatted rich HTML.
3. **Content Security Policy (CSP as Defense-in-Depth):**
   - Delivered via HTTP response header: `Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedscripts.com; object-src 'none';`.
   - Restricts where scripts, styles, images, and network connections can originate.
   - Disallows inline script execution (`'unsafe-inline'`) unless cryptographic nonces or hashes are supplied.
   - **Limitation:** CSP is an operational safety net that mitigates the blast radius of injection bugs; it does not replace proper output encoding and input validation.

## Cookie Security & Credential Protection

Cookies remain a primary mechanism for managing browser sessions. Proper cookie attributes configure how the browser stores and transmits credentials.

```
+-----------------------------------------------------------------------------+
|                              Cookie Attributes                              |
+-------------------+---------------------------------------------------------+
| HttpOnly          | Blocks client-side JavaScript (`document.cookie`) access.|
| Secure            | Directs the browser to transmit the cookie ONLY via     |
|                   | HTTPS encrypted connections.                            |
| SameSite=Strict   | Never sends the cookie on cross-site requests (even on  |
|                   | top-level incoming link navigations).                   |
| SameSite=Lax      | Sends cookie on top-level safe GET navigations, but      |
|                   | blocks on cross-site POST/subrequests (default).        |
| SameSite=None     | Sends cookie on cross-site requests; REQUIRES `Secure`. |
+-----------------------------------------------------------------------------+
```

### Honest Limitation: What HttpOnly Does and Does Not Protect

- **What HttpOnly Does:**
  - Prevents an XSS script from directly reading the cookie value (e.g., `const stolen = document.cookie` returns an empty string or omits HttpOnly cookies).
  - Stops an attacker from exfiltrating the raw session token to an external command-and-control server.
- **What HttpOnly Does NOT Do:**
  - **Does not stop an XSS attacker from acting on behalf of the victim.**
  - If malicious JavaScript runs inside the victim's active session, the attacker script can call `fetch('/api/v1/transfer', { method: 'POST', body: ... })`.
  - Because the request is made from the authenticated origin inside the victim's browser, the browser **automatically attaches the HttpOnly cookie** to the outgoing request.

## Same-Origin Policy (SOP) & CSRF

### The Origin Tuple
The browser defines an origin strictly by the three-tuple:
$$\text{Origin} = \langle \text{Protocol}, \text{Domain}, \text{Port} \rangle$$

| Origin A | Origin B | Same Origin? | Reason |
| :--- | :--- | :--- | :--- |
| `https://example.com:443` | `https://example.com:443` | **Yes** | Exact match |
| `http://example.com` | `https://example.com` | **No** | Protocol mismatch (`http` vs `https`) |
| `https://example.com` | `https://api.example.com` | **No** | Domain/subdomain mismatch |
| `https://example.com:443` | `https://example.com:8443` | **No** | Port mismatch |

### SOP Core Rule: Read Isolation
Under SOP, a script loaded from Origin A (`https://evil.com`) is strictly prohibited by the browser from reading the response content, DOM, or local data of Origin B (`https://bank.com`).

**The Classic SOP Bank Example:**
1. A user logs into `https://bank.com`, establishing an authenticated session cookie.
2. In another browser tab, the user visits `https://evil.com`.
3. Script on `https://evil.com` executes: `fetch("https://bank.com/account/balance")`.
4. The browser sends the request to `bank.com` along with the user's session cookie.
5. `bank.com` responds with the account balance.
6. **SOP Enforcement:** The browser intercepts the response and blocks `evil.com`'s JavaScript from reading the payload.

### CSRF vs SOP
- **SOP protects data reads; it does not inherently prevent cross-origin writes.**
- In a classic Cross-Site Request Forgery (CSRF) attack, `evil.com` uses an HTML `<form action="https://bank.com/transfer" method="POST">` or simple script to trigger a state change.
- The browser submits the request and attaches ambient session cookies. Even though `evil.com` cannot read the resulting response, the server has already executed the money transfer.
- **CSRF Defense:** Anti-CSRF synchronizer tokens, custom request headers (e.g., `X-Requested-With`, `Authorization: Bearer <token>`), and `SameSite=Strict` / `SameSite=Lax` cookie configurations.

## Cross-Origin Resource Sharing (CORS)

CORS is a browser-enforced protocol that allows a server to explicitly relax SOP and authorize specific cross-origin frontends to read its responses.

```
+-------------------------------------------------------------------------+
|                        CORS Request Classification                      |
+-------------------------------------------------------------------------+
| Simple Request     | Safe methods (GET, HEAD, POST) with standard       |
|                    | headers and simple content types. Dispatched       |
|                    | directly without preflight.                        |
+--------------------+----------------------------------------------------+
| Preflighted        | Non-simple methods (PUT, DELETE, PATCH) or custom  |
| Request            | headers (Authorization, X-Custom-Header) or        |
|                    | Content-Type: application/json. Requires OPTIONS.  |
+-------------------------------------------------------------------------+
```

### Simple Requests vs Preflight Requests

1. **Simple Requests:**
   - **Methods:** `GET`, `HEAD`, `POST`.
   - **Allowed Headers:** CORS-safelisted headers (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`).
   - **Allowed `Content-Type` Values:** `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`.
   - **Behavior:** The browser dispatches the actual request immediately, including the `Origin` header. When the response arrives, the browser checks `Access-Control-Allow-Origin`. If invalid, the browser hides the response from JavaScript.

2. **Preflighted Requests:**
   - Triggered whenever a request uses methods like `PUT`, `DELETE`, `PATCH`, custom headers (such as `Authorization`), or `Content-Type: application/json`.
   - **Step 1 (Preflight):** The browser automatically issues an `OPTIONS` request first, carrying `Access-Control-Request-Method` and `Access-Control-Request-Headers`.
   - **Step 2 (Validation):** If the server approves via matching `Access-Control-Allow-*` headers, the browser dispatches the actual request. If the preflight fails, the actual request is never sent.

### Credentialed Requests & Origin Restrictions
When frontend JavaScript includes credentials (`credentials: 'include'` in `fetch` or `withCredentials = true` in `XMLHttpRequest`):
- The server must respond with: `Access-Control-Allow-Credentials: true`.
- **Strict Rule:** `Access-Control-Allow-Origin` **cannot be a wildcard (`*`)**. The server must explicitly reflect or allow the exact requesting origin (e.g., `Access-Control-Allow-Origin: https://app.example.com`).

## Honest Limitations: Common Architectural Misconceptions

```
+-----------------------------------------------------------------------------+
|                      Critical Web Security Misconceptions                   |
+------------------------------------+----------------------------------------+
| Misconception                      | Reality                                |
+------------------------------------+----------------------------------------+
| "CORS protects our server from     | CORS is a client-side browser read     |
| unauthorized API calls."           | policy. Non-browser clients (curl,     |
|                                    | Postman, botnets) ignore CORS entirely.|
+------------------------------------+----------------------------------------+
| "CORS stops malicious sites from   | Simple POST requests reach and execute |
| modifying server state."           | on the server before CORS headers are  |
|                                    | evaluated by the browser.              |
+------------------------------------+----------------------------------------+
| "HttpOnly cookies make our app     | An XSS payload can still issue API     |
| completely safe from XSS harm."    | requests from the victim's session with|
|                                    | cookies attached automatically.        |
+------------------------------------+----------------------------------------+
| "CORS is needed for backend-to-    | Backend server-to-server calls do not  |
| backend microservice calls."       | run inside browsers; CORS does not     |
|                                    | apply to them.                         |
+------------------------------------+----------------------------------------+
```

1. **CORS is NOT Authorization or Authentication:**
   - CORS is a browser mechanism to protect the user's browser session from unauthorized cross-origin reading.
   - Any external client using `curl`, Python `requests`, or Postman does not enforce SOP/CORS and can send arbitrary requests. All APIs must enforce authentication (JWT, session token, API key) and role-based authorization on the server.
2. **CORS Does Not Reliably Stop State-Changing Simple Requests:**
   - If a cross-origin site issues a simple `POST` request (`Content-Type: application/x-www-form-urlencoded`), the browser sends the payload immediately without preflight.
   - The backend processes the request and executes the database write. When the response returns without `Access-Control-Allow-Origin`, the browser merely prevents client JavaScript from viewing the returned data. The server side-effect has already completed.
3. **Backend-to-Backend Exclusion:**
   - If your Java Spring Boot microservice calls the Stripe API or another internal microservice, CORS is completely irrelevant. CORS is strictly enforced by web browsers.

## Quick recall

**Q. Does TLS prevent XSS attacks?**
A. No. TLS secures transport in transit against eavesdropping and tampering. In XSS, the server itself delivers the malicious payload or the client DOM executes it locally.

**Q. If JavaScript cannot read an HttpOnly cookie, how is the cookie actually used?**
A. The browser itself automatically attaches the HttpOnly cookie to outgoing HTTP requests (in the `Cookie:` header) matching that domain and path.

**Q. Does using HttpOnly cookies completely prevent an XSS attacker from causing damage?**
A. No. While the attacker cannot extract the raw cookie string, their injected script can still issue authenticated requests (`fetch`/`XHR`) from the victim's browser session, and the browser will attach the HttpOnly cookie automatically.

**Q. What is the difference between Context-Aware Output Encoding and HTML Sanitization?**
A. Output encoding converts special control characters to display entities so untrusted data is treated strictly as plain text. Sanitization parses and filters HTML to allow safe formatting tags while stripping malicious elements, and is used only when rich HTML input is required.

**Q. If a simple cross-origin POST request violates CORS, does the backend still execute the state change?**
A. Yes. Simple requests are sent without a preflight `OPTIONS` check. The server processes the request and executes the write. The browser only blocks client-side JavaScript from reading the response.

**Q. Why is `Access-Control-Allow-Origin: *` prohibited when `Access-Control-Allow-Credentials: true` is configured?**
A. Allowing wildcards on credentialed requests would allow any malicious origin on the internet to read sensitive, user-specific authenticated responses. Browsers require explicit, non-wildcard origin allowlisting for credentialed sharing.

**Q. Is CORS used to secure backend-to-backend API calls?**
A. No. CORS is strictly enforced by web browsers. Server-to-server HTTP clients do not enforce SOP or CORS policies.
